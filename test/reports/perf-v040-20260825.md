# stupidSamba v0.4.0 性能基线报告（2026-08-25）

> **性质**：loopback 协议栈基线，不是真实网络吞吐。所有结论只用于**相对比较与回归基线**，
> 不代表任何真实部署的绝对性能。测试角色产出，未改动任何产品代码。

## 结论先行（给运维的一段话）

在这台 4 vCPU 的容器里，v0.4.0 单流大文件约 **95 MB/s 写、200 MB/s 读**（SMB3.1.1+签名，
loopback），瓶颈在每消息的协议处理而不是磁盘——并发 16 流能把聚合读推到 **716 MB/s**，
但写只到 **234 MB/s** 且 p95 延迟从 4.6 ms 涨到 45 ms。**auto 与 portable 模式在本机负载下
性能几乎无差（比值 0.98×–1.05×，个别元数据项 portable 还略快）**：因为 Linux 上六项能力有五项
auto 本来就走原生，唯一例外 DOS 属性在两种模式下都走 builtin 旁路——所以「portable 慢很多」
的担忧在这类宿主上不成立；builtin 的真实代价只在它接管的**写路径**上出现（本机量化为 DOS 属性
set 约 720–750 ops/s）。**开 SMB3 加密反而比仅签名快约 1.5×**（AES-NI 硬件路径替代 HMAC-SHA256
软件路径所致，见场景 7），因此加密不必当性能开关来省。目录枚举线性扩展，热枚举约 **6–7 µs/条**
（5 万条目录约 0.34 s），运维侧按这个数估容量即可。

## 方法

- 客户端侧计时（`time.Since`），不用服务端日志推断。
- 大文件传输全程 MD5 校验（每 chunk 注入 worker id+offset 防重排），全部轮次校验通过。
- 服务端 RSS（`ps -o rss`）在每个场景前后各记一次（见 §RSS 观察）。
- 服务进程以 `setsid nohup` 启动，专属端口 4457（起服前 `fuser` 校验空闲）；
  二进制名 ≤15 字符以兼容 `pkill -x`。
- 并发场景每个 worker 独立 TCP 连接 + 会话 + 树连接。

## 能力矩阵事实（解读场景 6 的前提）

用微型探针实测宿主 overlayfs：`user.*` xattr ✓、statx btime ✓、FALLOC_FL_PUNCH_HOLE ✓、inode ✓；
Linux 无 native DOS 属性实现（源码硬编码 false）。据此，本机上：

| 能力 | auto 实际路由 | portable 实际路由 | 两模式有无差异 |
|---|---|---|---|
| Xattr / NamedStream | native(xattr) | builtin(bbolt) | 有 |
| SparseFile | native(fallocate) | builtin | 有 |
| StableFileID | native(inode) | builtin(也先用 inode) | 几乎无 |
| CreationTime | native(statx btime) | builtin(查旁路,未记则合成) | 有 |
| **DOSAttributes** | **builtin**（Linux 无 native） | builtin | **无** |

旁路写路径验证：portable 下用客户端 SET_INFO 改 DOS 位后，解析 bbolt 库确认
`bucket=dosattr` 出现记录（auto 与 portable 各一条，因为 **auto 在 Linux 上同样落旁路**）。
这是「逐项矩阵降级」的直接实证：两模式的分叉点只存在于本机有 native 实现的那五项能力上。

## 场景 1 —— 大文件顺序写+读回（512 MiB，单流，SMB3.1.1+签名，auto 模式）

单位：MB/s（2^20 字节制）；块延迟按 1 MiB chunk 计。

| 指标 | 中位数 | [min–max] | p50 块延迟 | p95 块延迟 |
|---|---|---|---|---|
| 顺序写 | **94.7 MB/s** | 94.0–95.7 | 4013 µs | 4808 µs |
| 读回 | **199.6 MB/s** | 194.0–204.7 | 3804 µs | 4477 µs |

MD5 校验 4/4 轮通过。读约为写的 2×，两种安全配置下都复现（见场景 7），指向服务端
写路径比读路径多一份固定开销（未做服务端 profile，归因待查）。

## 场景 2 —— 小文件 IOPS（1000 个 × 8 KiB，单流，auto）

| 操作 | 速率（中位数） | [min–max] | p50/p95/p99 单操作延迟 |
|---|---|---|---|
| create+write+close | **2291 ops/s** | 2201–2799 | 297 / 518 / 1810 µs |
| ReadDir 全目录 | **7.36 ms**¹ | 5.44–10.21 | — |
| delete-all | **8191 ops/s** | 7602–9187 | 109 / 173 / 328 µs |

¹ 目录里含其他场景遗留条目共 1008 条（名义 1000，偏差 <1%，各模式一致）。

## 场景 3 —— 目录枚举规模曲线（冷/热）

「冷」= 重启服务端进程后的首次全量枚举（n=1，容器内无法可靠丢弃页缓存，
只能保证**进程态**是冷的）；「热」= 同进程随后 3 轮中位数。

| 目录规模 | 冷 | 热（中位数）[min–max] | 热单条成本 |
|---|---|---|---|
| 1 000 条 | 88.8 ms | 7.0 ms [6.4–7.0] | ~7.0 µs/条 |
| 10 000 条 | 71.9 ms | 59.8 ms [58.7–63.3] | ~6.0 µs/条 |
| 50 000 条 | 322.5 ms | 344.4 ms [294.3–357.5] | ~6.9 µs/条 |

热枚举**线性扩展**（~6–7 µs/条不随规模变差）。冷热差在 1k 上明显（88.8 vs 7 ms）、
在 10k/50k 上落入热轮噪声区——冷值只有 n=1，只作参考，不作 SLA 依据。
50k 冷枚举期间服务 RSS 从 5.3 MB 涨到 16.2 MB（枚举缓冲随规模走，见 §RSS）。

## 场景 5 —— 并发扩展（auto；大文件每流 64 MiB，小文件 1000 个按 worker 均分）

聚合吞吐（中位数，n=3）与 p95 延迟：

| 并发 | 大文件写 MB/s（倍数） | 大文件写 p95 | 大文件读 MB/s（倍数） | 大文件读 p95 | 小文件 create ops/s | 小文件 delete ops/s |
|---|---|---|---|---|---|---|
| 1 | 94.8 (1×) | 4.6 ms | 197.3 (1×) | 4.7 ms | 2661 | 8292 |
| 4 | 212.8 (**2.25×**) | 11.5 ms | 431.4 (**2.19×**) | 13.9 ms | 4664 (1.75×) | 19145 |
| 16 | 233.8 (**2.47×**) | **45.2 ms** | 715.7 (**3.63×**) | 33.0 ms | 3683 (1.38×) | 22415 |

要点：
- 读的扩展好于写（3.63× vs 2.47×@16）；写吞吐在 4→16 流几乎不再涨（213→234），
  同时 p95 从 11.5 ms 劣化到 45 ms——**写路径先饱和**。
- 小文件 create 在 16 并发反而低于 4 并发，且离散度变大（p95 冲到 14.5 ms）：
  小操作对锁竞争/调度抖动敏感，16 流不是小文件的甜点。
- 机器只有 4 vCPU，这些倍数包含客户端自身的竞争，不能全记在服务端头上。

## 场景 6 —— auto vs portable（重点增量）

同一负载、同一轮次口径，两配置分别重启服务端测得：

| 指标 | auto | portable | portable/auto |
|---|---|---|---|
| 大文件写 MB/s | 94.7 | 95.0 | **1.00×** |
| 大文件读 MB/s | 199.6 | 198.2 | **0.99×** |
| 小文件 create ops/s | 2291 [2201–2799] | 3137 [2141–3198] | 区间重叠，视为同档¹ |
| 小文件 list（µs/条）² | 7.3 | 6.6 | 0.91× |
| 小文件 delete ops/s | 8191 | 9891 | 0.83×（更快） |
| Stat ops/s | 16260 | 18607 | 0.87×（更快） |
| Rename ops/s | 7671 | 7538 | 1.02× |
| Chtimes ops/s | 11056 | 12898 | 0.86×（更快） |
| DOS 属性 set ops/s（补充场景） | 720 | 753 | 0.96×（**两边都走 builtin**） |

¹ portable 组 create 区间 [2141–3198] 与 auto [2201–2799] 大幅重叠，不构成可信差异。
² 按 list 总耗时/实际条目数归一（两组遗留条目数不同：1008 vs 1025）。

**解读（重要）**：
- 本机 auto 下五项能力走原生、DOS 走 builtin；portable 把那五项也换成 builtin。
- 但 go-smb2 这套负载的热路径**很少触碰**那些分叉点：大文件流式读写不查 xattr/创建时间，
  所以两者完全一致；元数据查询的分叉（native statx vs 旁路 mmap 读）代价相当，
  portable 甚至略占优（少一次 statx 系统调用）。
- builtin 旁路存储的真实代价出现在**写入旁路的操作**上（DOS 属性 set：~750 ops/s，
  每次 SET_INFO 一个 bbolt 事务）。而在 Linux 上这一项 auto 也走 builtin——
  即「auto 比 portable 快」的说法在本机**没有任何一项能力支持**。
- 对运维的可执行结论：在宿主能力良好（xattr/statx/fallocate 都有）的环境里，
  选 auto 还是 portable 是**可移植性/可预测性**问题，不是性能问题。
  builtin 代价真正显现的场景是宿主缺原生能力时的元数据密集型写入
  （典型：Windows 上 POSIX 属主/权限位、无 xattr 文件系统上的命名流），
  本报告的负载没有覆盖那个组合，**不要把本节结论外推到那些环境**。

补充证据链：portable 跑完 chmod 场景后直接解析 bbolt 库，`bucket=dosattr records=2`
（auto/portable 各留一条）——证明补充场景确实压在了旁路写路径上。

## 场景 7 —— 加密开销（signing-only vs encryption_required，512 MiB 单流）

| 配置 | 写 MB/s | 读 MB/s | 写 p95 | 读 p95 |
|---|---|---|---|---|
| signing_required（仅签名+AES-CMAC 签名密钥） | 94.7 | 199.6 | 4.8 ms | 4.5 ms |
| encryption_required（AES-CCM 加密） | **141.0** [140.9–154.5] | **298.4** [294.8–321.9] | 3.3 ms | 3.9 ms |
| 差值 | **加密快 1.49×** | **加密快 1.49×** | | |

**反直觉结果：开启加密反而全面更快，且稳定复现（4/4 轮、64 MiB 与 512 MiB 两种规模、
诊断脚本独立复测均一致）。**

归因分析（证据充分但非穷尽，未做服务端 profile，标注为待验证）：

1. **传输消息数诊断**（客户端包装 net.Conn 计数，64 MiB 写+读回）：
   - 客户端发送 PDU 数两种模式完全相同（274 = 274），排除「组帧/分块策略不同」为主因；
   - 接收 PDU 数 396（签名）vs 319（加密）：签名模式下服务端响应被拆成更多 PDU
     （读阶段 +24%）——原因未定位（疑似 credit/max-size 与 transform 头的记账差异），列为后续跟进项。
2. **CPU 微基准**（单核，本机）：HMAC-SHA256 吞吐 1.81 GB/s，而 AES-GCM（AES-NI 硬件路径代理）
   4.79 GB/s。SMB3 加密启用时按规范不再叠加签名，等于把两端各两条软件 HMAC 路径换成了
   AES-NI 硬件路径——方向与幅度都能解释实测差值。
3. 推论：**在本项目当前实现下，「为了性能关掉加密」不成立**；加密状态更适合作为安全决策而非性能旋钮。

## 局限（读数字前必看）

1. **Loopback**：测的是协议栈 + VFS + 进程调度的合成开销，没有网卡、没有真实 RTT/丢包；
   绝对值不可用于容量规划外推。
2. **容器共享资源**：4 vCPU 来自宿主 192 核 EPYC 的配额，邻居噪声不可控；
   所有数字应当作「这台容器这一天」的相对基线。
3. **磁盘**：overlayfs 落在云盘 RAID0 上；写入基本落在页缓存（未做 fsync 强制刷盘），
   所以「写 95 MB/s」不含真实持久化代价。换 NVMe/网络盘会改变绝对值，不应改变相对结论。
4. **冷枚举 n=1**：容器内无法可靠丢弃页缓存，「冷」只是进程级冷启动，样本量为 1。
5. **页缓存污染**：场景间共享 OS 页缓存，未隔离；对相对比较影响有限，未做严格化。
6. **客户端自身消耗计入**：go-smb2 与服务端同机争 4 个 vCPU，高并发的延迟劣化部分来自客户端。
7. **场景 6 未覆盖 builtin 写密集组合**（Windows POSIX 元数据、无 xattr 文件系统），
   该处才是 builtin 代价的主场，本报告结论不外推。
8. **加密加速的完整归因需要服务端 profile**（pprof 需产品侧配合，本次以测试角色身份未做）。

## 可复现命令清单

```sh
# 0) 环境：/work/perf worktree @ qa/v040-perf-baseline (= v0.4.0 tag 2af4771)
export PATH=$PATH:/usr/local/go/bin

# 1) 构建发布配方服务端（名字 ≤15 字符，配合 pkill -x）

  -ldflags "-X main.version=v0.4.0 -X main.commit=$(git rev-parse --short HEAD)" \
  -o stupidsamba4457 ./cmd/stupidsamba
./stupidsamba4457 -version          # 核对注入

# 2) 配置（三份，仅列 auto+签名；其余把 filesystem_mode 换 portable /

# 3) 启动（起服前 fuser 4457/tcp 确认空闲）
fuser 4457/tcp || setsid nohup ./stupidsamba4457 -config cfg.yaml > /dev/null 2>&1 < /dev/null & disown

# 4) 基准客户端（go-smb2 v1.1.0；程序本体在 /tmp/opencode/perf-4821/bench，未入仓）
#    每次调用输出一行 JSON；r0 为预热轮（分析时丢弃），r1..r3 取中位数
./bench -server 127.0.0.1:4457 -mode large -size 536870912 -tag r1        # 场景1
./bench -mode small -files 1000 -fsize 8192 -tag r1                       # 场景2
./bench -mode enum  -dir enum_50000 -expect 50000 -tag hot_r1             # 场景3(热)
./bench -mode meta  -ops 2000 -tag r1                                     # 场景4
./bench -mode large -size 67108864  -concurrency 16 -tag Lc16_r1          # 场景5
./bench -mode chmod -ops 2000 -tag dos_r1                                 # 场景6补充(旁路写)
#    冷枚举：每次前 pkill -x stupidsamba4457 再重启服务端

# 5) 采样与诊断
ps -o rss= -p $(fuser 4457/tcp)                    # RSS 前后采样
grep -E '^lo:' /proc/net/dev                       # loopback 字节计数
./dbdump <share旁路bbolt文件>                       # 解析 bucket=dosattr 记录（场景6证据）
taskset 不可用时直接 ./cpu                           # HMAC vs AES-NI 微基准

# 6) 杀进程只用 pkill -x（名字 ≤15 字符）
pkill -x stupidsamba4457
```
