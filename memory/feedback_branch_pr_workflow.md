---
name: 团队改用独立分支 + PR 流程
description: v0.1.0 之后每个 agent 必须在自己的分支上开发并走 PR 合并，禁止直接推 main
type: feedback
---

**从 v0.1.0 发布之后的所有开发开始，团队中每个 agent 使用自己独立的分支，
走提 PR、评审、合并的流程，禁止直接向 `main` 推送。**

用户原话：「从下个版本的开发开始，团队中使用自己独立的分支开发，
不要共用一个分支了，走提 PR，合并的流程。」

**Why:** 共用一个工作树 + 共用 `main` 已经反复造成两类真实事故：
1. 别人未提交的中间态让 `go build` 报出根本不存在的错误——真实发生过某 agent
   分两步做重命名，中间约 1 分钟工作树是 `undefined: xxx`，另一个 agent 撞上后
   排查了一个不存在的 bug。
2. 不合规/半成品代码可以一路畅通进 `main`，直到发布前才被发现——
   v0.1.0 发布前就撞到 CI 的 gofmt 门禁在 HEAD 上已经是红的，
   以及 `test/` 目录因为 build tag 从未被任何校验覆盖过。

分支 + PR 把「进主干」变成一道显式关卡。

**How to apply:**
- 分支名 `<agent 角色>/<简短主题>`，如 `auth/smb30-encryption`、`vfs/named-streams`。
- 「尽快提交尽快推送」的纪律**不变**，只是推送目标从 `main` 变成自己的分支——
  环境随时崩溃，未推送的工作依旧永久丢失。
- PR 要小、能独立编译通过，一个 PR 只做一件事。合并前 CI 必须绿。
- 对**自己的**分支允许 `--force-with-lease`（不是 `--force`）；对 `main` 一律禁止强推。
- **分支隔离的是提交历史，不隔离工作树。** 若多个 agent 仍共用同一个工作目录，
  §7 的文件所有权划分照旧生效，不能因为「我在自己分支上」就去改别人的文件。
- 规则已写入仓库 `AGENTS.md` §7.3（该文件是本项目最高准则）。
