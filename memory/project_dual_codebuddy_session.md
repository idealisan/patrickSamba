**开工前先自检有没有重影进程**：

```sh
grep -h sessionId /root/.codebuddy/sessions/*.json | sort | uniq -c
```

同一个 `sessionId` 出现 **≥2 次**，就说明有两个 `codebuddy` 进程挂在同一会话上。
**必须先处理再开工**，否则整轮并行开发的产物都不可信。

**Why：** 2026-08-09 实测事故。`codebuddy -y -c`（`--continue`）**不检查该 session 是否已经有活着的进程占着**，
会直接再挂一份上去。`~/.codebuddy/sessions/<pid>.json` 里两个不同 pid 写着同一个 `sessionId`，
两个进程各自心跳、各自跑一整套子 agent。

机制上的后果是**两个 team-lead → 两套同名 agent**（两个 `oscap-native`、两个 `win-meta`、两个 `release`……），
它们拿着**同一份 prompt**，于是**各自都在「自己的」`/work/<role>` 里干活**。
危险点在于：这种破坏形态下**没有任何一方越界** —— 每个 agent 都严格待在自己该待的目录里，
所以 **§7.3.1「不许写别人的工作目录」这条纪律从原理上就防不住它**。这是把它记下来的全部理由。

## ⚠️ 边界：以上是**机制推演**，本次事故并未证实真的发生过互相覆盖

这一条最初被我写成「双进程造成了 4 次写冲突」。**那个因果结论是错的，已撤回。** 反证有两路，互相独立：

1. **PM 的写入审计**：对事故窗口内全部 **363 次文件写入**逐条核对 owner 与路径，
   **跨 owner 写入 0 次**。
2. **进程活跃度对账**：影子进程 `2710370` 在整个并存窗口只产出 **24 行**工具相关日志，
   本体 `2732263` 是 **6627 行**。影子基本是**空转**的，它没在写东西。

那 4 起「冲突」的真身是**误判**（把 rebase 产生的 dangling 提交、未跟踪的在制品、
以及 team-lead 自己的只读评审副本，都当成了「别人写进来的」）。

**同时要记住：事后归因这条路在本项目是走不通的。** 两个实例共用同一个 committer 身份
（都是 `FinalTape`），提交里没有任何字段能区分是哪套实例写的；PM 对 3 棵 twin 树做 `merge-base`
溯源也只能判断「提交在不在某分支的祖先链上」，判断不了「谁写的」。
**既然事后查不清，唯一有效的手段就是开工前那次自检** —— 这也是为什么本条的重点是预防命令，
而不是取证流程。

共享状态分两档，**别混为一谈**（本次事故正是因为混谈才误判了 4 次）：

**已证实被损坏 —— codebuddy 自己的状态：**
- `~/.codebuddy/projects/<proj>/file-history/<sessionId>/` —— 日志里 **158 处**
  `[FileVersionStore] Failed to file: <hash>@v1, error=ENOENT`，是被另一方清掉的。
- `~/.codebuddy/projects/<proj>/<sessionId>/subagents/` —— 两套同名 agent 的记录混在一起，
  事后想区分「这段是哪个实例的」已经不可能。

**机制上有风险，但本次查无实据 —— 你的代码：**
- `/work/*` 各工作树。**没有任何一棵被跨 owner 写过**（363 次写入逐条核对，0 次跨界）。

这两档的实际含义完全不同：**双进程弄脏的是工具的记账，不是仓库里的代码。**
所以撞上这种情况时，正确反应是「清理进程 + 不信任会话记录/文件历史」，
**不是**「怀疑代码被污染、推倒重做」—— 后者会白白丢掉磁盘上真实有效的成果。

## ✅ 后续实证（2026-08-09 18:26，vfs-deflake）：**同名同树的交叉写入真的发生了**

上面说的是「跨 owner 写入 0 次」，那个结论**仍然成立**，但它**测不到**下面这种形态 ——
两套实例是**同名**的，写的是**同一棵**工作树，按 owner 归属逐条核对时它们**长得一模一样**，
于是全部记为「合规」。**审计方法本身对这个形态是盲的**，别把「0 次跨界」读成「没有互相干扰」。

实测经过：我（`vfs-deflake`）在 `/work/vfs-deflake` 编辑 `test/ci/check-test-compile.sh`，尚未提交；
18:26:28 分支上凭空出现提交 `f6952a7`（另一套同名实例做的 `internal/vfs/path_perf_test.go` 重构），
它用 `git add -A` 提交并推送，**把我那份在途改动一并卷了进去**。
后果不是「文件被覆盖」，而是：

1. **两个人的改动混进同一个提交**，而提交信息只描述了其中一半 —— 评审时极具误导性；
2. 那个提交**同时改了已划归他人的目录**（`internal/vfs/` 当时刚划给 `oscap-wire`），
   事后按提交记账会把这笔算错人头。

**发现它靠的是一个反直觉的信号：`git status` 该脏却显示干净。**
明明刚 Edit 过文件，`git status --short` 却空白 —— 说明有别人替你提交了。
**在共享/可能有重影的环境里，「干净」不等于「没事」，它同样可能是「已经被别人收走了」。**

因此在上面的开工自检之外，再加两条：

- **每次 Edit 之后、下一步动作之前，先看一眼 `git status --short` 是否与预期一致。**
  预期该脏而实际干净 = 有第二个写入者，立即停下来查 `git log --oneline -3`。
- **提交前先 `git status --porcelain` 看清将要提交什么，不要盲跑 `git add -A`。**
  这次的直接成因就是对方盲跑了 `git add -A`。自己的改动散落在多个目录时，
  优先 `git add <明确路径>`，把「顺手带走别人东西」的概率降到 0。

**没有丢失任何工作**（两边改动都完整无损、合并后本地全绿），所以处置同上：
清进程 + 不信任工具记账，**不要推倒重做代码**。

## ✅ 第 2 例（2026-08-09 19:06，pm）：**同一份活被做了两遍，产出互相矛盾**

形态与 18:26 那例同源（同一棵树 `/work/pm-r2`、对方 `git add -A` 把我三处未提交改动
一并卷进它的提交 `bd46181`），但暴露出**一个 18:26 那例没有的危害维度**：

> **写入者身份没查出来，别照抄「双进程」这个成因。** 事发后 19:13 的自检
> `grep -h sessionId .../sessions/*.json | sort | uniq -c` 计数是 **1**——**没有**第二个进程
> 同挂 session。也就是说本条标题那个机制**不是**本例的已证成因；committer 全队共用
> `FinalTape`，事后无从区分。**可观测的只有「有第二个写入者且在做同一份活」这件事本身。**

- 两个实例**并行做了同一轮巡检**，各自写板子：出现两套 `§19.15.x` 编号、
  同一个记忆文件里两个「null 陷阱」小节、
  以及**两份给 team-lead 的合并顺序建议，结论相反**（`#159→#153→#155` vs `#155→#159→#153`）。
- **代码一个字节都没丢**，丢的是**结论的唯一性**。对 PM / 评审 / 文档这类
  「产出即决策依据」的角色，**自相矛盾比缺失更糟**：缺失会被追问，矛盾会被随机采信一份。

**识别信号（比 18:26 那条更早触发）**：`git log --oneline -3` 里出现**你没写过、但主题与你
高度重合**的提交，且时间就在几十秒内。18:26 那例的信号是「`git status` 该脏却干净」——
两条一起用：**干净得反常、或历史里多出一笔像自己写的提交，都是重影信号。**

**收尾方式（本次采用，供照抄）**：不要两套都留，也不要粗暴覆盖对方。
逐节比对，**保留信息更全的那一份，把自己独有的部分并进去，重复的整段撤下**，
并在文档里显式写明「哪一版作废、为什么」——否则读者会以为两套都还生效。

**How to apply：**
- 每轮组队开工前跑一次上面的自检命令；发现重影就 `kill <旧pid>`（**普通 SIGTERM 即可**，实测一发就退）。
  **不要用 `pkill -f codebuddy`** —— 那个模式会匹配到执行它的 shell 自己，把自己一起杀掉。
- 判断哪个是旧的：`ps -o lstart= -p <pid>` 比开始时间，或看 `sessions/<pid>.json` 的 `startedAt`。
  杀之前确认它**无子进程**（`ps --ppid <pid>`）且**未持有工作树文件**（`ls -l /proc/<pid>/fd | grep /work`）。
- 事后判断某轮成果是否被重影污染：查 `~/.codebuddy/logs/<日期>/<proj>__<hash>.log`，
  按分钟统计出现过的 pid：
  ```sh
  grep -oE '^\[[^]]+\] \[[A-Za-z]+\] \[pid=[0-9]+\]' "$LOG" \
    | sed -E 's/^\[[0-9/]+ ([0-9]{2}:[0-9]{2}):[0-9]{2}[^]]*\] \[[A-Za-z]+\] \[pid=([0-9]+)\]/\1 \2/' \
    | sort -u | awk '{a[$1]=a[$1]" "$2} END{for(k in a) print k, a[k]}' | sort
  ```
  一行里出现两个 pid = 那一分钟有重影。

## 附：「崩溃」这个词要分清丢什么、不丢什么

本项目长期的认知是「容器会崩溃并清空 git 以外的一切」。**2026-08-09 这次不是那种崩溃**，
误判会导致白白重做已经存在于磁盘上的工作。区分方法：

| 判据 | 容器真重启 | 只是 codebuddy 进程死了（本次） |
|---|---|---|
| `uptime` | 从头计时 | 连续（本次 up 8:55，从未重启） |
| `/work/*` worktree | 没了 | **全在**（本次 50 个全在） |
| `~/.codebuddy/projects/.../*.jsonl` | 没了 | **全在**（会话与 subagent 记录都在） |
| 丢的是什么 | 一切仓外文件 | **只有进程本身和它的 in-process agent** |

所以复工第一步应当是 `uptime` + `ls /work`，而不是假定一切归零。
真崩溃的恢复走 `scripts/restore-history.sh` + `codebuddy --resume=<uuid>`（**不要用 `-c`**，见上）。

## 附：死因排除法（本次查不到，就写查不到）

进程 `2732263` 在 `16:40:50` 的正常流式输出后**无任何错误、无退出日志**地消失。能排除的：
- **不是容器重启**：`uptime` 连续。
- **不是 cgroup OOM**：`/sys/fs/cgroup/memory/memory.failcnt` = **0**（从未触及上限）；
  上限 4 GiB，峰值 `max_usage_in_bytes` = 3.54 GiB（88.5%，很险但没爆）。
- **不是 node 堆溢出**：死前 `rss=769.6MB heap=363.8/522.6MB`，日志无 `JavaScript heap out of memory`。
- **无法确定**：形态符合被外部信号突然打断（控制终端消失的 SIGHUP，或 SIGKILL）。
  容器内 `dmesg` 不可读、无 audit 日志。**拿不到直接证据就写「查不到」，不要编一个死因。**
