**默认仍然是「保留优先」**，但 `history/` / `codebuddy-files/` / `conversation-*.txt`
这一类**已被所有者明确移出仓库**（见「2026-09-20 反转」）。现行口径见文末。

**Why（原有理由，仍然成立）**：用户两次明确纠正过我的"清理"倾向——

1. `conversation-*.txt`（会话导出文件）——我曾误判为误提交并执行 `git rm --cached` +
   加入 `.gitignore`。用户当时纠正：「会话导出文件是我故意提交的，作为项目历史资料
   很重要，要加进去，以免丢失记录」。
2. `v0.1.0-test` 测试 Release——releng 计划验证完就 `--delete --delete-tag` 清掉，
   我照转了这个方案。用户纠正：「跑 v0.1.0-test 但是别删，如果通过再发一个不带 test
   后缀的不就行了，干嘛要删，这是珍贵的工作记录和历史资料」。

背后的逻辑：**保留的成本几乎为零，丢失则不可逆**。这与本项目「容器随时崩溃、
仓外一切不可信」（AGENTS.md §10）的处境高度相关——用户对"丢记录"警惕性很强。

## 2026-09-20 反转（现行口径）

项目所有者当天指示：「把仓库里不该出现的 history、codebuddy 相关的目录排除掉，
并且历史 commit 里也清理掉」。据此：

- `history/`（实测工作树 **138 MB**、115 个文件）、`codebuddy-files/`、根目录
  `conversation-*.txt` → **从工作树排除（磁盘保留）+ 加入 `.gitignore` +
  用 git filter-branch 从全部历史提交中清除**。
- 决策依据（实测数字，非臆测）：`history/` 单文件 20 MB；`.cnb.yml:66-72` 明确记着
  它是「目前最大的一处浪费」——每次入库都会把 12 关整套跑一遍。
- **因此本文件原来的第 1 条「永远不要删除…或把它们加入 `.gitignore`」作废。**
  不要再拿它当依据拒绝执行，也不要反过来把其它「历史痕迹」一并清掉。

## How to apply（现行）

- `history/` / `codebuddy-files/` / `conversation-*.txt`：**不入库**；要归档就落到
  **仓库之外**的持久位置（`scripts/save-history.sh` 的默认落点尚未调整，属待办，
  见 `.gitignore` 里的 ⚠️ 注释）。
- 其它「记录了工作过程」的产物（测试性 tag / Release / 构建产物）**仍然一律保留**，
  不要"用完即删"；发正式版另打一个干净的。
- 提出方案时默认仍是"保留"；确实要删/要清历史时，**先说明理由、列出准确范围并
  征求同意**（体积/成本这类理由要给出实测数字），再动手；动手前先落备份
  （备份 ref + bundle），并把「磁盘保留」作为默认选项。
- 清理**临时构建中间物**（`/tmp` 下的 worktree、`dist/` 重建产物）不受此约束——
  区别在于它们不记录任何工作过程。
- 教训：记忆里的旧规矩可能已被所有者推翻。**遇到「旧规矩 vs 新指令」冲突时，
  以新指令为准，但必须把冲突摆到台面上确认**（本次即如此）——不要默默照旧、
  也不要默默照新。
