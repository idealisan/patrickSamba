name: 内容门的覆盖面 = 探针的位置，只能证明探针所在那一处落地了
description: 用内容门判「某 PR 是否已合」时，探针选在哪就只证明哪一处；PR 含多个部件时会得出「已合」的半真结论
type: feedback
---

内容门（查 main 上是否存在某段内容）能绕开 squash 与 SHA 漂移，是判「事情是否发生」的正确工具。
**但它只能证明探针所在的那一处落地了，不能证明整个 PR 落地了。**

**Why:** 2026-08-09 队友用内容门验证 `#152` 是否合入：探针取脚本内部的两个独有串
（`isDangerousBashCommand`×7、`patch-codebuddy.status`×2），命中，结论「#152 已 squash 合入 main」。
复验发现只对了一半 —— 该 PR 有两个部件：**脚本本体**和 **`.cnb.yml` 里调用它的挂接**。
脚本确实进了 main，但 `git show origin/main:.cnb.yml | grep -c patch-codebuddy` = **0**，挂接根本没进。
真实状态是「脚本在仓库里，但没人自动跑它」，而结论却被读成「这件事做完了」。
差点据此删掉文档里「开工第一件事仍需手工跑一次」那句**仍然正确**的提示 ——
那会把一句真话换成假话，属于文档不诚实的反向形态。

**How to apply:**
- 下探针前先问：**这个 PR 由几个部件构成？** 每个部件在 main 上各有一个独立可查的痕迹吗？
  部件多于一个，就要多于一个探针，或者明确写清「本判据只覆盖 X」。
- 探针优先选**该 PR 唯一新增/唯一删除**的那一处，零歧义；
  跨文件的 PR 则每个文件各取一处（脚本取函数名，YAML 取调用行，文档取那句独有的话）。
- 报结论时把探针位置一并写出来：「脚本部分已合（探针：脚本内 X）；挂接未合（探针：`.cnb.yml` 的 Y = 0）」，
  不要只写「#152 已合」。**半真的「已合」比「没合」更危险**，因为它会让人去删除仍然有效的提醒。
