文档诚实性审计不能只往「有没有夸大」一个方向查。**反向的失真同样是错，而且更隐蔽，
因为它读起来很谦虚，抽查时会通过。** 2026-08-09 v0.2.0 发版前审计逮到四种形态：

**Why:** 夸大会被用户用「我试了不行」当场戳穿，反向失真不会——用户只会绕开这个功能
或换个方案，代价是**沉默的**。所以它能在文档里活很久，而且越谦虚越没人质疑。

**How to apply:** 审计每条断言时，除了问「有没有说大话」，还要问这三句：

1. **「这句『未实现』今天还成立吗？」——谎报未完成。**
   实例：`README.md` 的 Time Machine 节写于 v0.1.0，把 durable/persistent handle
   列在「未实现」并标注「对 TM 影响最大」，而 v0.2.0 的头号新增就是它（PR #20/#40/#29）。
   判据：拿 CHANGELOG 当期章节与 README 的「未实现」清单**对撞**，重合项即命中。

2. **「这是现在的事实，还是接线/合并之后才会发生的事？」——未来时写成现在时。**
   实例：队友转述「POSIX 上 `filesystem_mode: native` 恒定启动失败」，我实跑真二进制
   得到相反结果（rc=124 照常启动）——因为 main 上 oscap **没有运行期消费方**，
   报错逻辑根本执行不到。那个结论只在他**已接线的分支**上成立。
   **纪律：队友转述的「实测」必须问清跑在哪条分支/哪个 commit 上**，
   不同分支的实测结论互相矛盾是正常的，直接抄进文档就成了假话。

3. **「已知问题」是所有文档里最容易腐烂的一节。**
   它天然记录「还没做的事」，而那恰恰是别人此刻正在做的事。
   实例：我写「6 个文件从未被编译过」并附注「若有人修了记得改，否则变成谎报未完成」，
   十几分钟后 `e664a47` 真的在 main 修掉了。**发版前必须逐条重跑判据，
   不能沿用审计当时的结论。**

4. **注释/文档里的「见 X」必须当断言核实——X 可能压根不存在。**
   实例：`test/ci/check-test-compile.sh:113` 写「负向对照见 `test/ci/negative-verify.sh`
   的 freebsd 段」，而那个文件里 `grep -c freebsd` = **0**。我第一遍照抄进 CHANGELOG，
   复核时才发现。**危害方向和前三种相反：它会主动劝阻后来者去补**——
   读到那句的人认为反向对照已经存在，于是不写了。
   判据：凡「见 / 详见 / 参见 + 具体实体名」，都要 `grep` 一次那个实体真的在。

**配套做法：给每条能力标注证据强度，替代含糊的「已支持 / 部分支持」。**

| 档 | 含义 |
|---|---|
| A | 目标平台真机端到端实测 |
| B | 第三方客户端协议级实测（impacket / smbclient / go-smb2） |
| C | 仅本仓库单测覆盖 |
| D | 代码存在，但没有任何一关执行过它 |

分档的价值在于**它逼你把 D 档说出口**——「代码写了」和「验过了」用同一个词描述，
正是绝大多数文档失真的源头。
