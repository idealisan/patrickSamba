## 背景（为什么改）

2026-08-09 约 15:54–16:40，两个 codebuddy 进程（pid 2710370 + pid 2732263）**同挂同一个
session `2d8786c5-5251-4e43-9fd4-6d9ec5a77103`**（证据：`/root/.codebuddy/sessions/2710370.json`
与 `3923374.json` 的 `sessionId` 字段均为该值；2732263 是其中一方，在 15:54–16:40 窗口内与
2710370 并存，log 中 2732263 有 57447 行、2710370 有 273 行）。

`codebuddy -c`（--continue）与 `--resume=<uuid>` **都不检查这个 session 是否已经有活着的进程占着**，
会直接再挂一份。**已证实的后果只有一类：工具侧的记账被两方共写弄坏**——
同一份 `file-history` 被另一方清掉/覆盖，log 中可直接看到：

```
[2026/8/9 08:37:23.949] [Error] [pid=20451] [FileVersionStore]
  Failed to file: 5c63c92aac136c99@v1, error=ENOENT: no such file or directory,
  open '/root/.codebuddy/file-history/2d8786c5-5251-4e43-9fd4-6d9ec5a77103/5c63c92aac136c99@v1'
```
（同一 session 的 file-history 被另一方清掉/覆盖过；该碰撞模式在 log 中共 158 处。）

本次崩溃中报告的「win-meta 工作树里有别人在跑 C9 探针」「release 工作树里出现外来提交
`60620c3`」「oscap-native 工作树里出现非自己写的 Windows 文件」等四起冲突，
**曾被归因于这套 phantom twin，该因果已于 17:35–17:45 撤回**：

- 窗口内 9 个并发 agent 共 **362 次**确认落盘写入，按树的真实归属判定**跨 owner = 0**；

- 68 个 `agent-*.jsonl` 按角色名归并，窗口内**每个角色恰好 1 个实例**，第二套同名 agent 不存在。

四起各有机制级自伤证据（编译错误行号 / pid / reflog / mtime），逐条见 §18.3。
容器从未重启（`uptime` 当时 8:55+，现 9:10+），这一条仍然成立。

## 修订草案一：§7.3.1 新增「开工前先查重影进程」（更根本的一道）

在 §7.3.1「开工第一件事」之后插入：

> **开工前自检（已观察到的危险信号，先于一切文件操作）**：
> 在开 worktree、改任何文件之前，先确认本 session 没有第二个 codebuddy 进程挂着：
> ```sh
> grep -h sessionId /root/.codebuddy/sessions/*.json | sort | uniq -c
> ```
> 若**同一个 sessionId 出现 ≥ 2 次**，说明有重影进程同挂本 session。
> **已证实的后果是工具侧记账损坏**（file-history 撞 ENOENT）与白占内存；
> 「两套同名 agent 共写工作树」**在本项目已被实测证伪，不要拿它当既成事实**。
> 处置：**先确认那个旧进程是死的还是空转的**（比对两个 pid 的工具类日志行数），
> 再决定 kill 还是请示 team-lead，**不要默认它正在破坏你的树**。
>
> **⚠️ 同时要知道：这件事「事后归因不可行」。** 一旦真的发生了同挂，
> 你**没有任何办法**从产物上区分「哪一笔改动出自哪个实例」：
> - 两个实例共用同一个 committer 身份（本仓库都是 `FinalTape`），`git log --format=%an %ae` 分不开；
> - commit / 工作树文件里**没有任何字段**记录进程实例；
> - `git merge-base --is-ancestor` 只能判「这笔在不在历史里」，判不了「这笔是谁写的」。
>
> 所以这条自检的价值**全在事前**：撞见 ≥2 就当场处理掉。
> 事后再想查「是不是那个重影干的」，只能像 §18.9 那样去翻 `agent-*.jsonl` 的工具调用记录做统计推断，
> 代价极高且只能给出总体结论（跨 owner 有没有、有多少），**给不出单笔归属**。

## 修订草案二：§7.3.1 保留「只读评审副本不许写别人 `/work/<role>`」（仍有效）

> **只读评审副本的纪律**：任何人需要做「只读评审复现」（例如对照别人的改动在自己机器上跑一遍），
> 必须在**自己的目录**或 `/tmp/<自己的名字>-<用途>` 下做**只读 checkout**，**严禁向别人的
> `/work/<role>` 写任何文件**。评审复现放 `/tmp/<自己的名字>-<用途>`，不要碰 `/work/<别人的角色>`。
> 理由：即便本意是只读，一旦在工作树里落笔（哪怕临时文件、临时改一行），就会污染 owner 的工作树，
> 在 phantom twin 场景下还会被误判成「冲突」。

（注：`/tmp/lead-native` 那次是 team-lead 本人建的只读评审副本，结论照写不误；本条款约束所有人，
包括 team-lead。）
